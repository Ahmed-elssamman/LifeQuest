## Pre-existing issues

- Baseline dependency installation reported 20 advisories (2 moderate, 18 high). A scoped override now uses patched js-yaml 5.4.2 for Swagger, and the lockfile uses patched http-cache-semantics 4.3.0. The production-dependency audit reports zero vulnerabilities. Seventeen high advisories remain in development dependencies, mainly through Nx and tsc-alias. Their direct roots are the latest published `braces` and `node-forge` releases as of 2026-10-04; npm's suggested remedies would downgrade direct tools across major versions. CI now runs a hard production audit and a full-audit baseline check that fails on any new high or critical package/advisory while reporting the 17 known development-tool findings. This is an explicit residual risk, not a claim that the full audit is clean.
- Nx daemon failed on the first baseline build. Nx disabled it; the build passed. A fresh build after edits passed with daemon and cache disabled.
- Existing Vercel packaging deploys the API as a function and disables email. Split routing is a separate option.
- Render Free sleeps when idle. In-process challenge, attachment, and expired-record maintenance is not guaranteed through sleep. Persistent feedback storage requires operator configuration.
- The owner confirmed `lifequest-web` and `lifequest-admin` as the MIRHAL Vercel targets. The live aliases `https://lifequest-web-cyan.vercel.app` and `https://lifequest-admin.vercel.app` both return 200 and map to Ready production deployments in those linked projects. The customer deployment still includes a Vercel API function. No Render API origin or live Render/email values were available for the split deployment.
- The owner confirmed the Neon URL in the ignored local `.env` as the production database. A read-only status check initially found four pending migrations: `202610040001_arabic_default`, `202610040002_quest_template_arabic`, `202610040003_builtin_content_arabic`, and `202610040004_shared_rewards_arabic`. Their SQL was reviewed as additive. A custom-format `pg_dump` archive was saved under the ignored `.local/backups/mirhal-prod-pre-arabic-20261004.dump` with mode 600 and verified by `pg_restore --list`. `npm run db:deploy` then applied all four without error; `prisma migrate status` reported up to date, and the existing Vercel `/api/health` remained HTTP 200. The archive contains production data and must stay private.
- Aggregate checks on that Neon database found all seven shipped achievements, four shared rewards, one quest template, three quest steps, and five season phases translated. There are currently no untranslated quest templates or steps, achievements, season phases, announcements, or shared rewards in those tables; no announcement rows exist. These checks do not cover user-entered content or future editorial records.
- Arabic quest-template descriptions and steps were missing even though titles were bilingual. An additive migration now adds these fields and backfills the shipped reference template. Older custom templates need Arabic copy in the admin editor before Arabic customers can see them.
- Shipped achievement, journey phase, and shared reward copy had English-only descriptions or names. Additive migrations and seed data now supply Arabic fields and backfill those records. Older custom content still needs editorial translation; untranslated announcements remain hidden on Arabic dashboards.
- Registration still returns an account-exists conflict for duplicate addresses. Login and password reset responses avoid account enumeration, but registration behavior remains an abuse-review item because changing its API contract requires coordinated UX work.
- Registration currently creates a session and starts onboarding in the same response. A generic duplicate-address response would still be distinguishable from a successful registration by the missing session and user data. Hiding it properly requires an email-first registration redesign and a coordinated client contract change; the existing five-per-minute route limit remains the current mitigation. Password recovery returns the same status and body for known and unknown addresses, but synchronous delivery can still produce a timing difference. A durable asynchronous delivery design or a live timing review is needed before claiming full enumeration resistance.
- Task ancestor traversal now scopes each lookup to the authenticated owner, matching the reference validation and update path. A broader manual authorization and abuse review is still open.
- A targeted authentication review confirmed HttpOnly, Secure-in-production, host-scoped session cookies; database-backed production rate limits on public auth endpoints; one-use recovery tokens; and password-reset session revocation. Registration's duplicate-address response and the different work performed for known versus unknown password-reset addresses leave account-enumeration risk to assess before a public launch. The API now also caps verification and recovery token creation at five per account and purpose per hour using the existing PostgreSQL token records and a user-row lock. The route-level limits still depend on client identity resolved from the hosting proxy.
- Render client identity for rate limiting remains unverified. `clientTracker` trusts Vercel's client header only inside a Vercel function; on Render it uses Express `request.ip`. With the planned Vercel rewrite in front of Render, multiple visitors might share a proxy address and therefore a rate-limit bucket. Do not enable broad proxy trust or accept an untrusted forwarded header without verifying the live hop chain. Test distinct clients and the direct Render origin before calling the production abuse controls complete.
- A targeted ownership review found reward redemption, refund, rating, and favorites scoped to the signed-in user or shared reward; friendship actions require membership, and challenge actions require participation. Declining a challenge currently cancels the whole challenge; its lifecycle code processes all participants when activated, so changing that behavior requires coordinated lifecycle work. Feedback attachment uploads now check ownership and the three-file limit before writing to storage, then recheck in the transaction to handle races. This prevents foreign or over-limit requests from causing storage writes.
- A route-level source review found account/profile/export operations bound to the authenticated user, planning and habit mutations checked by owner, quest item completion checked against the owner's quest, notifications and feedback filtered by user, and reward history filtered by user. Admin routes use role guards; writes also recheck staff access in their database transaction. Private feedback downloads require the owner or an allowed staff role. Integration tests cover representative cross-user access and support-role restrictions, but this review does not prove every possible object reference or future route safe.

## New regressions

None known in completed checks. The full browser suite passed (22/22), including customer and admin dialog layout tests at 320 and 360 px in both languages. A local Vercel artifact check confirmed the customer API route points to a sample Render origin, the admin route points to the customer origin, and split mode omits the legacy Vercel cron/function. The sample outputs were removed from the linked artifact folders after inspection so they cannot be deployed by mistake.

The Render deployment packaging now has its own command, `npm run vercel:package:render`, which requires exact HTTPS web, admin, and API origins before writing artifacts. The legacy Vercel function packaging remains available through `npm run vercel:package` for the existing deployment path. A missing API origin failed before writing artifacts. A fresh build with sample origins produced the expected customer-to-Render and admin-to-customer routes, with no legacy function or cron; those sample outputs were removed immediately after inspection. Real-origin deployment remains unverified.

The worktree passed typecheck, lint, 42 unit tests, 79 integration tests (including concurrent callers at the account email budget and strict production origin validation), 35 frontend tests, fresh Angular and Nest builds, SSR verification, Prisma validation and migration parity, and the full browser suite (22/22). The API was rebuilt after the auth, startup validation, and email template changes. Browser checks cover every primary customer and admin route in Arabic and English at 11 widths, plus accessibility, registration, onboarding, administration, challenges, recovery, primary customer and admin creation dialogs at 320/360 px, and both email HTML variants at 320 px; they are not a complete visual review of every dialog or inbox client. Prisma Client generation and the production dependency audit also passed, with zero production vulnerabilities reported. The four shipped shared rewards, seven achievements, and five season phases were confirmed translated in the isolated test database. Audit action and entity labels were checked against every current backend audit write. The customer initial bundle measured 551.43 kB (140.56 kB estimated transfer); its reviewed warning threshold is 560 kB, with the 800 kB error limit unchanged. A tracked-file pattern scan found only placeholder database URLs in the example environment file and local database helper; the configured secret-value scan found no matches.
